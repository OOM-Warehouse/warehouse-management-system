## A. Architecture and packages

**Stack:** Spring Boot 3.2.1, Java 17, Maven. Dependencies: data-jpa, web, thymeleaf (+ `thymeleaf-extras-springsecurity6`), security, mail, validation, devtools, H2 (runtime), flyway-core, Lombok (optional), jaxb-runtime (provided). Tests use spring-boot-starter-test (JUnit 5, Mockito, AssertJ) and spring-security-test. Nothing else is available offline.

**Style:** a server-rendered layered MVC monolith (Controller → Service interface → ServiceImpl → Spring Data repository → JPA entity → H2). Thymeleaf renders the pages. There is one JSON endpoint (`/api/suggestions`).

**Persistence:** Flyway owns the schema. Migrations are `src/main/resources/db/migration/V1__baseline.sql` (DDL generated by Hibernate 6.4) and `V2__stock_adjustments.sql`. Hibernate runs with `ddl-auto=validate`, `ImplicitNamingStrategyLegacyJpaImpl` and `PhysicalNamingStrategyStandardImpl`. IDs use `GenerationType.AUTO`, which gives one sequence per table (`<table>_SEQ`, increment 50). The dev DB is a file H2 at `./data/warehouse`. Tests use in-memory H2 (`src/test/resources/application.properties`) with Flyway enabled.

**Frontend:** 67 Thymeleaf templates under `src/main/resources/templates/`, grouped by module (`items/`, `vendors/`, `customers/`, `purchaseOrders/`, `salesOrders/`, `goodsReceiptNotes/`, `pickingJobs/`, `putAwayTasks/`, `stockAdjustments/`, `reports/`, `admin/`, `auth/`, `dashboard/`, `search/`, `error/`). Shared fragments are `header`, `navbar` (sidebar), `footer` and `pagination`. Styling is Bootstrap. List pages share one "Advanced search" modal pattern.

## F. Missing functionality

1. **Shipment / delivery tracking:** no `Shipment` (and no `ShipmentLine`) entity, carrier, tracking number, shipped/delivered timestamps, delivery status lifecycle, UI or reports. This is core to the assignment.
2. **Sales order status lifecycle:** runtime code never sets `PARTIALLY_SHIPPED` or `SHIPPED`. The only transition is a side effect inside `SalesOrderServiceImpl.updateById` (PARTIALLY_SHIPPED → SHIPPED when backorders are empty), and nothing ever reaches PARTIALLY_SHIPPED in the first place.
3. **Backorder resolution:** backorders are created but never consumed. When the follow-up picking job is fulfilled, the original `Backorder` rows remain, and a second shortage creates duplicates. There is no backorder list or UI.
4. **Stock availability check / reservation** at SO creation. Orders can exceed on-hand stock, and nothing checks or allocates.
5. **Partial goods receipt flow:** PARTIALLY_RECEIVED is defined but unreachable (G-2), and the receive POST accepts only IN_TRANSIT POs.
6. **Invoice UI** (list and details). An invoice-by-customer report is in `requirements.docx` but not implemented.
7. **Warehouse / section management UI** (CRUD), and capacity per section.
8. **Bean Validation on domain forms:** only the auth and admin DTOs use `@Valid`. Item, vendor, customer, PO, SO, GRN, picking, put-away and adjustment forms bind entities without validation. Negative or zero quantities, over-receipt beyond PO qty, and blank names are all accepted.
9. **Domain-level exceptions** for business-rule failures, such as insufficient stock, an invalid status transition, or an already-fulfilled GRN or picking job. `IllegalStateException` and `null` returns are used instead.
10. **Item cost UI** (`ItemCost` is seeded only), and no overlap check on price or cost periods.
11. **Reorder → PO automation** (reorder candidates are shown on the dashboard only).

## G. Bugs, code smells, architecture problems

### Correctness bugs (high → low)

| # | File:line | Defect | Failure scenario |
|---|---|---|---|
| G-1 | `Services/PickingJobServiceImpl.java` `fulfill()` (~l.180–215) | Calls `pickingJob.getPickingJobLines().remove(i)` inside an index-based `for` loop | The next line is skipped, and DTO index `i` no longer lines up with entity line `i`. With 2+ out-of-stock lines, a line is silently ignored, or picked against another line's section and qty |

### Code smells

- `@Column(name=...)` on `@OneToMany` collections and on methods (`formattedAddress`). These are ignored and misleading.
- Typo field `WarehouseSection.pickingJobLinesw`. `SoStatus` comments (`//0, //2, //3`) do not match the ordinals.
- Ordinal enum persistence (`GrnStatus`, `PjStatus`, `PoStatus`, `SoStatus`) with DB `CHECK (status between 0 and n)`. Reordering or inserting values corrupts data, and adding a value needs a migration.
- `System.out.printf` debugging in `InvoiceServiceImpl` and `Bootstrap`.
- Dead code: `Services/GoodsReceiptNoteImplBack.java` (fully commented out), `templates/forms/*` (unused legacy forms including `fulfillGoodsReceiptNoteFormBack.html`), unused DTOs (`NewSalesOrderDto`, `ItemCostDto`, `WarehouseSectionIdDto`), and large commented-out blocks in controllers and `StockRepository`.
- `buildSpec` id / text-mode matching is copy-pasted across 7 services (DRY violation).
- Magic strings `"00-00-0-0"` and `"11-11-1-1"` are duplicated across `GoodsReceiptNoteImpl`, `PutAwayController` and `Bootstrap`.
- `ItemPool` contains duplicate SKUs (e.g. 423456, 434567, 445678), and `item.sku` has no unique constraint.
- Entities are bound directly as `@ModelAttribute` (mass-assignment risk; no validation).
- Anemic domain model: totals exist, but no invariants or state transitions on the entities.

### Architecture problems

- Business orchestration sits in controllers (picking → stock → invoice), with no single transactional use case.
- No domain events or state machine for order lifecycles.
- Service → repository fan-out (6 repos per service) instead of collaborating services.

## J. Compatibility risks

1. **Flyway + `ddl-auto=validate`**
   - Any new or renamed column, table or type needs `V3__*.sql` or later. Never edit V1 or V2. Validation also checks column **types**: `double` maps to `float(53)`, enum ordinal to `tinyint`, `Instant` to `timestamp(6) with time zone`.
   - A new enum constant on an ordinal status requires dropping and re-creating the `CHECK (status between 0 and n)` constraint. In H2 the generated constraint names are unknown, so prefer appending constants at the end and writing a migration that alters the constraint, or add new statuses as `@Enumerated(STRING)` in new columns or tables only.
   - New entities need a matching `<table>_SEQ` sequence (increment 50) because of `GenerationType.AUTO`.
2. **`@MappedSuperclass` refactor:** moving `@Id @GeneratedValue(AUTO)` into a base class keeps per-entity sequences (resolved per entity table), so it should be schema-neutral. This must be proven by `WarehouseManagementApplicationTests.contextLoads` (validate) and the `@DataJpaTest`s. Column names must stay identical (`name`, `street`, `city`, `state`, `zipcode`, `contact_info`). `@Embeddable Address` is also schema-neutral if column names are preserved. JPA table inheritance (SINGLE_TABLE or JOINED) would need a migration and is not justified.
3. **Lombok `@Data` on entities:**
   - Generated `equals`/`hashCode`/`toString` traverse bidirectional associations (`Item`↔`ItemPrice`, `SalesOrder`↔`SalesOrderLine`, …), which risks `StackOverflowError` and lazy-loading of whole graphs when logged or put in `Set`s.
   - Any base class needs `@EqualsAndHashCode(callSuper=…)` decisions, and `@SuperBuilder` instead of `@Builder` if builders must set inherited fields.
   - Changing `@Builder` to `@SuperBuilder` changes builder types that `Bootstrap`, the services, the seed pools and the tests use extensively.
   - `@Builder.Default` must be kept on collections, or builders produce `null` lists.
4. **Spring Security:**
   - CSRF is enabled (default) for every POST except `/h2-console/**`. New MockMvc POST tests need `.with(csrf())` and `@WithMockUser`. New Thymeleaf forms must use `th:action` so the token is injected.
   - `/admin/**` requires ADMIN; all other routes only require authentication.
   - `@WebMvcTest` slices load `SecurityConfig`, which needs a mocked `UserService`, `EmailService` and `TwoFactorAuthenticationSuccessHandler` dependencies, as the existing tests do.
   - Known weaknesses: the H2 console is `permitAll`; `EmailServiceImpl` logs 2FA codes and reset links on SMTP failure (dev fallback); `Bootstrap` seeds `admin / Password123!`.
5. **Template coupling:** list pages rely on query flags (`?notFound`, `?cannotBeUpdated`, …) that `GlobalExceptionHandler` emits. New handlers should follow the same `redirect:/<list>?<flag>` convention. Templates index form lines by position (`Counter`), so changing collection order or size semantics (e.g. G-1 fixes) must keep the DTO/entity index alignment.
6. **Bootstrap in tests:** `@SpringBootTest` runs `Bootstrap`. Seeding changes (new entities or statuses) affect `WarehouseManagementApplicationTests` and the dashboard KPIs. `@DataJpaTest` does not run `Bootstrap`.
7. **Native SQL:** many reports and KPIs are native H2 SQL using ordinal status numbers (e.g. `purchase_order.status = 0`). Changing enum storage or order breaks them silently, and only some are covered by the repository tests.
8. **Offline build:** no new dependencies. Run only `mvn -o test` (no `clean`). MapStruct, state-machine libraries, ArchUnit and similar cannot be added.
